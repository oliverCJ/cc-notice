# CC Notice 板卡接入

使用本 skill 接入或更新 CC Notice 内置板卡。用户提供的板卡信息只能作为线索，不能直接作为事实来源；公开板卡必须优先用官方资料校准。

当前可落地路线是“内置板卡接入”：固件、Board Catalog、Pin Catalog、设备身份策略、通道能力、烧录 manifest、前端元数据、硬件说明、测试和文档必须随应用一起发布。当前版本不支持把任意用户固件放入本地目录后自动完成设备层接入。

## 必读上下文

在收集板卡事实或修改代码前，先读取：

- `docs/固件开发指南.md`
- `CLAUDE.md` 中关于固件、Board Catalog、Pin Catalog、设备身份、硬件说明弹窗、用户板卡包方向的内容
- `references/board-input-checklist.md`

如果这些文件存在冲突，执行更严格的规则，并在接入设计中说明冲突和取舍。

## 官方资料校验

公开板卡必须先查官方资料：

- 产品页
- 官方 pinout
- datasheet 或 schematic
- bootloader、上传、烧录说明
- Arduino FQBN、板卡包或 package index，适用时必须确认

优先使用官方资料，不要用第三方摘要替代官方事实。官方资料缺失或板卡为用户自制时，先要求用户补齐规格，再进入实现。

接入设计必须列出：

- 使用过的官方来源 URL
- 已确认的板卡事实
- 用户提供信息与官方资料的差异
- 仍需用户确认的缺失事实

## 工作流程

1. 读取必读上下文和输入清单。
2. 收集并校验官方板卡事实；官方资料不可得时，向用户索取完整规格。
3. 在改代码前输出简短接入设计，至少包含：
   - 官方来源、确认事实、冲突和缺失项
   - `boardId` 和展示名称
   - MCU、family、能力层级
   - 设备身份策略：`required`、`limited` 或明确不支持
   - 烧录策略、toolchain、manifest 产物选择方式
   - 通道集合、默认通道、只保留元数据的针脚
   - 同族或同物理板卡能力变体的继承、裁剪和保留针脚策略
   - 固件需要实现的协议命令
   - 设备识别、注册、连接和重连策略
   - 输入通道、输入绑定、GPIO 双模式和快捷键策略
   - IO worker、异步上行事件和通信监控接入策略
   - 硬件说明弹窗和针脚图策略
   - 预计修改文件
   - 测试和验证命令
4. 停止并等待用户确认，除非用户在当前对话中已明确批准这份具体设计。
5. 获批后读取 `references/onboarding-workflow.md`。
6. 在正式实现前创建或更新 `docs/` 下的日期进度文档。
7. 先写或更新测试，再实现代码。
8. 验证固件、manifest、Board Catalog、设备识别注册、连接重连、通道、固件页、规则页、说明弹窗、文档和 `CLAUDE.md`。
9. 在进度文档中记录验证结果；无法执行的验证必须写明前置条件缺失或跳过原因。

## 强制规则

- 不要把 RP2040 Pico 当作所有板卡的默认模型。
- 不要让固件在当前实现中动态定义通道；板卡事实、针脚事实和通道能力必须由软件 catalog 维护。
- 固件返回的 `board_id` 必须与软件 `boardId` 完全一致，并且必须存在于 Board Catalog、Pin Catalog 和固件 manifest 形成的接入闭环中。
- 未知 `board_id` 不能被当成完整支持设备接入；不能生成误导性的默认通道、规则选项或说明弹窗。
- 不要暴露固件不支持的针脚或动作；Board Catalog 暴露的通道必须能被对应固件处理。
- 同族或同物理板卡能力变体必须使用独立 `board_id`、独立 artifact 和独立 Board Catalog 能力声明，但实现应共享主体代码；变体只能因外设占用、初始化、屏幕尺寸或能力开关裁剪差异，不得复制整套协议或丢失共享层已有能力。
- 能力变体继承同族 GPIO 双模式能力时，必须继续暴露未被外设占用的普通 GPIO 输入/输出切换；被 OLED、屏幕总线、蜂鸣器、WS2812 或其它外设占用的针脚必须同时从普通输出候选和 GPIO 输入候选中移除。
- 通道 ID 必须稳定，不能依赖用户规则、串口路径或临时扫描结果。
- 串口路径、扫描资源和端口描述只能作为运行态信息，不能作为板卡身份。
- 新增板卡必须明确输入能力、输出能力和扩展能力；按钮、GPIO 输入、屏幕、蜂鸣器等不得混在输出规则中描述。
- 屏幕能力必须按屏幕尺寸和交互场景建模。只要固件声明 `deviceExtensions.display`，就必须实现并响应 `display_status`，因为输出规则页依赖该基础原语提供稳定的屏幕输出入口；固件可以自行决定 `display_status` 如何影响屏幕，例如大屏显示完整覆盖卡，小屏更新状态区，特殊屏只记录状态或按本地布局摘要显示，但不能 timeout 或假成功。`display_runtime` 表示设备长期显示的软件运行态，优先承载真实 Hook 后的最终统计和最近状态；`display_status` 表示输出规则触发的事件状态，不等同于运行态。若固件同时支持 `display_status` 和 `display_runtime`，必须明确二者共存策略：分区更新、状态卡短暂覆盖后回到 runtime，或其它确定行为；软件侧不能用跳过 runtime 或丢弃 status 来模拟这个行为。
- 屏幕 payload 必须按板卡 display 能力裁剪。声明 `deviceExtensions.display` 的内置板卡必须显式填写 `sizeClass`，取值为 `compact`、`small`、`medium` 或 `large`；缺失值只允许作为历史数据兼容兜底，运行时默认按 `small` 处理。`compact` 适合 128x32 OLED 等极小屏，使用模板短句和 `E/O 事件数/输出数`；`small` 适合 128x64 OLED 等 2-4 行短文本；`medium` 适合 Wio 这类可显示完整摘要、多行文本和统计页的屏幕；`large` 预留给更大屏幕。`sizeClass` 只用于上位机选择文案详略，不约束固件内部布局，固件可以自由选择分区、覆盖卡或其它显示方式。不要复用 Wio、大屏或多行屏的长文案后暴力截断。
- 设备通道是设备 I/O 通道，不是单纯输出通道。固定按钮、五向键和 GPIO 输入必须归入输入能力，配置保存在设备级输入绑定中，不得放入输出规则或 Profile。
- 固定输入通道必须声明为不可切换输出；GPIO 双模式针脚必须声明输入/输出二选一，默认添加为输出。切换模式必须先进入待确认态，用户确认后才保存。
- GPIO 双模式 UI 和执行链路必须基于 Board Catalog、通道元数据或明确的板卡族系 helper 判断能力，禁止只用精确 `boardId` 写死普通 Pico、Wio 或其它单板分支，避免同族能力变体无法显示输入/输出切换。
- GPIO 输出切换为输入时，必须执行输出规则引用检查；被当前实现范围内的输出规则引用时必须阻止切换，并在设备通道面板就近提示。切回输出或移除输入通道时必须清理对应输入绑定。
- 已连接设备确认 GPIO 模式切换后，必须通过现有 IO worker 后台下发 `configure_input` 或等价配置命令；未连接设备只保存配置，并在连接成功后按当前输入通道配置同步给固件。通道保存流程不得串行等待多条硬件 ACK 导致 UI 卡顿。
- 固件若支持输入上行，必须实现稳定异步 `input_event`，并说明 `control`、`channel`、`action`、`seq` 字段。`input_event` 不是命令 ACK，ACK 读取层必须分流该事件并继续等待当前命令响应。
- 支持异步上行输入的串口读取路径，发送命令前不得清空输入缓冲导致 `input_event` 丢失；旧 ACK、噪声、空行和异步事件必须在 ACK 读取层归一分流。没有异步输入的复位噪声型板卡若仍需清理输入缓冲，必须在接入设计中说明边界和原因。
- 固件若支持 GPIO 输入配置，必须实现 `configure_input` 或在接入设计中说明为什么不需要动态配置。
- 输入绑定禁用后，设备通道记录和设备页输入测试区都必须显式显示禁用状态，避免用户误判为上行失败。
- 输入快捷键允许任意单键；组合键必须包含 `Control`、`Alt`、`Command`、`Shift` 或 `Win` 等修饰键，且只能有一个非修饰主键。前端键盘面板、后端校验和平台按键模拟必须使用同一键位范围。
- 设备页按钮上行测试区只能做输入通道与快捷键绑定的可视化验证，不得绕过真实设备链路伪造上行事件，也不得直接模拟触发键盘快捷键。
- 固定输入、GPIO 输入和屏幕本地按键用途必须区分：设备本地 UI 控制可以在固件内部消费部分按键，但声明为上位机输入能力的控件必须仍通过通用 `input_event` 上报，不得写成板卡专用事件或混入输出规则。
- 新增设备通信路径必须遵守 IO worker 单 owner 模型；监控、诊断和测试功能只能订阅旁路事件，不能直接打开同一串口。
- IO worker 等待 ACK 时必须匹配 ACK type 和 channel；worker 空闲读到非当前 ACK 的 JSON、旧 ACK、噪声或 `input_event` 时必须按协议分流或暂存，不能直接丢弃。
- 串口监控只能按已连接设备按需启动，未打开窗口时不得记录详细上下行事件、格式化 payload 或推送窗口事件。
- 同一设备只能有一个监控窗口；多设备监控必须有数量限制。设备断开后监控窗口保留并冻结记录，重连后从设备页再次打开应恢复或聚焦同一窗口。
- 监控窗口不得作为串口终端或事实来源；只能展示下行命令、ACK、timeout、`device_info` 查询、`input_event`、worker stop、连接和错误旁路事件。
- 监控事件展示顺序必须旧消息在上、新消息追加到底部；跟随滚动只控制滚动和自动选中新事件，不能暂停后端记录或丢弃事件。
- 设备通信错误必须归一为稳定枚举码或稳定字母码，禁止新增基于错误描述字符串的业务判断。
- 第三方串口库、操作系统和硬件返回的原始错误如只能以字符串获得，只能在明确的边界归一化函数内转换为设备错误码；业务层、诊断、自动连接、心跳和前端逻辑只能消费稳定 code，message 仅用于展示和日志。
- `stableUid: limited` 板卡必须验证 `set_device_uid` 或明确降级为 fallback 身份；`stableUid: required` 板卡不能用传输地址伪装稳定身份。
- Arduino 上传参数必须来自 `board.toml` 和 manifest，禁止在 UI 或命令层按板型猜测。
- 固件页必须按 artifact/target 选择产物，不要只按 `boardId` 假设单一固件。
- 固件页推荐标记、板卡族分组和能力层级是前端展示元数据，不得反向改写 manifest 或烧录策略；能力层级文案必须面向用户解释为完整、轻量、精简或扩展设备能力，不暴露 SRAM、协议字段等内部细节。
- 屏幕输出规则必须由上位机模板层决定业务内容，固件只实现显示原语。普通模式不得鼓励任意长自由文本；高级模板必须按目标设备 `textEncoding`、`sizeClass`、字段长度和最终 JSON 行字节上限裁剪，ASCII 设备必须有确定非 ASCII 降级策略。
- 用户可见文案必须走 i18n。
- 用户板卡包能力落地前，不要暴露“自定义固件”或“用户板卡包”的普通用户入口。
- 重要板卡或固件变更必须同步更新 `CLAUDE.md` 和 `docs/` 下的日期进度文档。

## 用户板卡包方向

用户可加载板卡包是未来能力，不是当前行为。当前新增板卡默认走内置板卡接入。若用户现在要求使用自定义固件，先说明该固件必须作为内置板卡接入，除非用户明确要求设计并实现未来的用户板卡包系统。
